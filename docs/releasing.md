# Releasing

Walden is released from a version tag. The tag is the only trigger that
publishes packages; a branch build cannot. This document is how a maintainer
cuts a release, what the automation checks, and what it deliberately does not
do.

[packaging.md](packaging.md) is the packages themselves.

## What a release contains

Every GitHub Release attaches the same set of files, named for the project,
the version, the platform, and the architecture:

| Artifact | Contents |
| --- | --- |
| `walden-<version>-macos-arm64.pkg` | unsigned macOS package, Apple Silicon |
| `walden-<version>-macos-x86_64.pkg` | unsigned macOS package, Intel |
| `walden_<version>-1_amd64.deb` | Debian package, amd64 |
| `walden_<version>-1_arm64.deb` | Debian package, arm64 |
| `walden-<version>.tar.gz` | committed source, `walden-<version>/` prefix |
| `SHA256SUMS` | SHA-256 of each of the files above |

Stable download URLs are
`https://github.com/eliascotto/walden/releases/download/v<version>/<artifact>`.
The Arch recipe checksums `walden-<version>.tar.gz` from that URL, not GitHub's
automatically generated tag archive.

A version whose Cargo version contains a hyphen (`0.1.0-rc.1`, tagged
`v0.1.0-rc.1`) is published as a GitHub pre-release and is not marked latest.

The supported Rust version is the `rust-version` field in `Cargo.toml`, kept
in lockstep with `rust-toolchain.toml`. CI installs that toolchain; it does
not use whatever rustc the runner has.

## Cutting a release

1. The change is on the default branch. CI on that commit is green.
2. `Cargo.toml` already states the version being released. The tag is not a
   second source of truth; it has to match.
3. Tag the commit and push the tag:

   ```console
   git tag -a v0.1.0 -m "Walden 0.1.0"
   git push origin v0.1.0
   ```

4. The Release workflow verifies the tag, runs the same checks as pull
   requests, builds every package in an isolated job, writes the source
   archive from the tagged commit, and publishes one GitHub Release with
   every artifact and `SHA256SUMS`. If any job fails, nothing is published.
5. Confirm the release page: every expected file is attached, the notes call
   the macOS packages unsigned, and a pre-release version is marked as such.

The working tree that is archived is the tagged commit. Uncommitted files,
`target/`, `dist/`, and the vendored catalog are not part of the source
archive.

## Release checklist

Walk this before pushing the version tag, and again after the GitHub Release
exists. Privileged smoke checks are in [testing.md](testing.md).

### Before the tag

- [ ] `Cargo.toml` `version` is the version being released
- [ ] `Cargo.toml` `description`, `license`, `repository`, and `rust-version`
      match the project
- [ ] `LICENSE` is present and matches the `license` field
- [ ] CI on the default-branch commit is green
- [ ] `scripts/check.sh` is green locally
- [ ] User documentation (`README.md`, `docs/usage.md`) matches `walden --help`
      and `walden status`
- [ ] Packaging, service-ownership, and releasing documents match the packages
      that will be built
- [ ] A release that changes the persisted-state schema migrates the previous
      version in this same release, and the schema smoke in
      [testing.md](testing.md) has been run from a previous-schema build

### After the tag, on the GitHub Release

- [ ] Every expected artifact is attached: two macOS packages, two Debian
      packages, the source archive, and `SHA256SUMS`
- [ ] Checksums in `SHA256SUMS` match the attached files
- [ ] Release notes call the macOS packages unsigned
- [ ] A pre-release version is marked as such and is not latest
- [ ] The source archive contains only committed files, with the
      `walden-<version>/` prefix, and does not contain `target/`, `dist/`, or
      the vendored catalog

### Manual platform verification

- [ ] Privileged smoke checklist in [testing.md](testing.md) passed on each
      platform you install and exercise for this release (deeper upgrade /
      recovery checks if packaging, daemon, or state changed)
- [ ] Unsigned macOS installation was tested against current Gatekeeper
      behaviour (the first open is refused; Open Anyway is required)

### Downstream recipes

- [ ] Arch `PKGBUILD` generated by the Release workflow checksums the
      published `walden-<version>.tar.gz`
- [ ] macOS package URLs and checksums printed by that workflow are enough
      for a Homebrew cask, if one is being updated
- [ ] No apt repository is expected; Debian packages are installed from the
      release

## What CI verifies

Pull requests and pushes to `main` run `.github/workflows/ci.yml`. Version
tags run that workflow and then `.github/workflows/release.yml`. What each
check covers, what is outside the matrix, and the privileged smoke checklist
are in [testing.md](testing.md).

Release-specific behaviour:

- Downloaded crates are cached. Compiled artifacts are not, so a restored cache
  cannot hide a failing build.
- Obsolete pull-request runs are cancelled when newer commits supersede them.
  A release run is never cancelled by a later event on the same tag.
- macOS x86_64 packages are cross-built on Apple Silicon runners. Linux arm64
  is built and tested natively on `ubuntu-24.04-arm`.

## Re-running a failed release

Re-run the failed Release workflow from the Actions UI. The publish job
deletes the GitHub Release for that tag if one already exists, then creates
it again with the full artifact set. It does not delete the git tag. Partial
uploads from an interrupted run cannot remain next to a newer set of files.

A packaging or test failure still stops publication: the publish job does not
run until every build job has succeeded and every expected artifact is
present.

## Downstream recipes

The Release workflow generates the Arch `PKGBUILD` after the GitHub Release
exists, from the published source archive, and prints the macOS package URLs
and checksums a Homebrew cask would need. It does not open pull requests, and
a failure there cannot change the GitHub Release that was just published.

To publish the Arch recipe, copy `dist/arch/PKGBUILD`, `dist/arch/walden.install`,
and `.SRCINFO` (when makepkg has generated it) into the AUR or project
repository. The `sha256sums` entry must remain the checksum of
`walden-<version>.tar.gz` from that GitHub Release, not of GitHub's
automatically generated tag archive. A Homebrew cask, if added later, points
at the two macOS package URLs and their `SHA256SUMS` entries the same way.

There is no automated apt repository. Debian packages are installed from the
release until repository signing and hosting exist.

## Signing later

The macOS package is already a distribution product, which is the shape
`productsign` and notarization expect. Signing is a job that takes the
unsigned `.pkg` and writes a signed copy; it does not change
`scripts/package-macos.sh` or the way artifacts are collected. Cosign or
similar for checksum files can sit next to `SHA256SUMS` the same way.

Until that job exists, the release notes state that the macOS packages are
unsigned.

## Branch protection

Once the workflows have run successfully on a pull request, protect the
default branch so that:

- The `CI` check (the aggregator job) is required
- Direct pushes that bypass a pull request are refused, or at least cannot
  skip the required check
- Version tags used for release are not moved

The workflows do not configure protection themselves.
